# 死循环根因分类学 (Deadloop Taxonomy)

## 1. 触发场景矩阵

| 场景 | 触发条件 | 死循环机理 | 发生频率 |
|------|----------|-----------|---------|
| 目录已存在 | `mkdir /path` → EEXIST | LLM 未识别为"已完成"，重新尝试 | ★★★★★ |
| 权限不足 | `mkdir /root/foo` → EACCES | LLM 尝试 sudo / chmod / 换路径 → 均失败后继续重试 | ★★★★ |
| 父目录不存在 | `mkdir /a/b/c` → ENOENT | LLM 逐层创建时某层失败，回退后重新从顶层开始 | ★★★★ |
| 磁盘满 | `mkdir` → ENOSPC | 文件系统元数据分配失败，Agent 清理后重试 → 仍满 | ★★★ |
| OOM / 进程被杀 | fork 失败 → 工具返回空 | LLM 收到空响应，认为"未执行"，重新调用 | ★★★ |
| I/O 阻塞 (D状态) | NFS/SMB 挂载点卡死 | 进程进入 D 状态永不返回，Agent 超时后重试 | ★★ |
| 工具崩溃 | bash 进程 segfault | 无 stderr 或 stderr 被吞，返回码异常但无文字 | ★★ |
| 路径名冲突 | 普通文件与目录同名 | `mkdir` 失败但 `test -d` 返回 false，Agent 困惑 | ★★ |
| 符号链接循环 | `mkdir` 经过符号链接 | 路径解析后指向不存在位置，反复创建失败 | ★ |

## 2. 死循环核心机理

### 2.1 信息不对称
```
LLM 期望: "已创建" 或 "失败原因"
工具返回: "" (空) 或 "Error" (模糊)
LLM 推理: "工具没有正确执行 → 需要重试"
```

### 2.2 状态不可观测
Agent 无法区分：
- "已经创建成功，返回了空" （重复创建 → EEXIST）
- "没有执行，进程没启动" （再试一次是正确的）
- "正在执行中，I/O 阻塞" （再试一次会加剧问题）

### 2.3 目标函数错位
LLM 的优化方向是"让 mkdir 成功"，而非"让目录存在"。

### 2.4 无代价意识
Agent 感受不到重试的累积代价（fork 失败加剧 OOM、I/O 阻塞进程堆积）。

## 3. 各 Agent 框架的 mkdir 死循环对比

| 框架 | mkdir 实现 | 死循环风险 | 备注 |
|------|-----------|-----------|------|
| Pi Agent | 裸 bash 调用 | **极高** | 仅 4 个工具，无封装 |
| Claude Code | BashTool + sandbox | 中等 | sandbox 提供错误结构化 |
| OpenCode | Primary/Subagent + Tool | 中等 | 子智能体可能独立死循环 |
| AutoGPT | Command 插件 | 高 | 插件质量参差不齐 |
| LangChain Agent | Python REPL | 中等 | 可用 Python 库替代 |

## 4. 关键洞察

**mkdir 只是一个症状，不是病根。**

真正的问题是 Agent 工具调用模型中缺少三个维度的信息通道：
1. **前置状态** — 调用前系统处于什么状态？
2. **后置状态** — 调用后状态是否满足预期？
3. **失败分类** — 如果不满足，原因属于哪一类？

任何工具如果只返回 "成功/失败" 布尔值，都会在边缘条件下诱发死循环。
